  而是**45 个测试样本对 3 分类来说太少了**，随机森林在这份小数据上很容易全对。
  真正的结论应该是："在这 45 个样本上零错误"，而不是"准确率 100%"。

## 三、阈值分析（自主功能的量化证据，实测 ✅）

```powershell
.\.venv\Scripts\python yuzhi_baogao.py
```

| 阈值 | 自动判定数 | 覆盖率 | 自动准确率 | 转人工数 | 转人工中本来判对的 |
| --- | --- | --- | --- | --- | --- |
| 0.00 | 45 | 100.00% | 100.00% | 0 | 0 |
| 0.30 | 45 | 100.00% | 100.00% | 0 | 0 |
| 0.40 | 45 | 100.00% | 100.00% | 0 | 0 |
| 0.50 | 45 | 100.00% | 100.00% | 0 | 0 |
| 0.60 | 43 | 95.56% | 100.00% | 2 | 2 |
| 0.70 | 41 | 91.11% | 100.00% | 4 | 4 |
| 0.80 | 35 | 77.78% | 100.00% | 10 | 10 |
| 0.90 | 29 | 64.44% | 100.00% | 16 | 16 |

### 这张表得出的结论（和预期不一样，如实记录）

原本预期是"阈值升高 → 覆盖率下降、自动准确率上升"。
**实测结果是：自动准确率一直是 100%，只有覆盖率在掉。**

原因很直接：随机森林在这 45 个测试样本上本来就全判对了，
没有"判错但很自信"的样本可以被阈值过滤掉。
所以提高阈值**只有成本、没有收益**——最后一列"转人工中本来判对的"
从 2 涨到 16，意思是阈值把 16 个**本来判对**的样本也推给了人工。

**这是一个真实且有价值的发现**，比编一个好看的趋势曲线更有说服力：

> 阈值机制只对"判错但置信度不高"的样本有用。
> 当一个模型在当前数据上已经接近零错误时，加阈值纯粹是浪费人工。
> 判断要不要上阈值，前提是先确认模型存在"高自信的错误"。

**边界说明**：以上只是 45 个测试样本上的统计，样本量很小，
不能作为任何通用结论。在真实业务里这个阈值该由误判代价推导，
不能看哪行数字好看。

## 四、依赖版本与文档推荐的差异（如实记录）

| 包 | 文档/指导书建议 | 实际装到 | 原因 |
| --- | --- | --- | --- |
| scikit-learn | 1.7.2 | **1.9.1** | Python 3.13 环境下 1.7.2 没有匹配 wheel |
| Streamlit | 1.50.0 | **1.64.0** | 同上 |
| pandas | 2.x | **3.0.5** | 同上 |
| numpy | — | 2.5.3 | — |
| pytest | — | 9.1.1 | — |

**这不是"照着文档没装对"**，而是 Python 3.13 版本较新，
旧版本包的 wheel 还没发布。已经做的处理：

1. `requirements.txt` 按 `pip freeze` 的**实际结果**写，不写推测版本；
2. 代码里没有依赖任何 1.7 → 1.9 之间被移除的 API，测试 40 条全过；
3. 元数据里记录了训练时的 scikit-learn 版本，加载时会校验主版本。

### 二次依赖安装的一个实际困难

直连 PyPI 时下载频繁超时（实测约 100~130 KB/s 且多次中断）。
最终改用阿里云镜像完成安装：

```powershell
.\.venv\Scripts\python -m pip install -r requirements.txt `
  -i https://mirrors.aliyun.com/pypi/simple/ `
  --trusted-host mirrors.aliyun.com
```

`scripts/anzhuang.ps1` 里已经把这个镜像作为默认值。

## 五、失败用例与修复记录

### 失败 1：pandas 3.0 不允许往 float64 列塞字符串

- **现象**：`test_piliang_huai_hang_bu_yingxiang_zhengpi` 报
  `pandas.errors.LossySetitemError` → `TypeError: Invalid value '坏数据' for dtype 'float64'`。
- **原因**：测试代码用 `biao.iloc[2, 0] = "坏数据"` 往一个 float64 列里塞字符串。
  pandas 3.0 收紧了类型转换（旧的 pandas 会静默把它变成 object 列），
  现在直接抛异常。
- **为什么这是"测试的问题"不是"被测代码的问题"**：
  真实场景里坏数据是从 CSV 读进来的，那一列本来就会是 object dtype。
  被测的 `yuce_piliang()` 逻辑没问题，是测试构造坏数据的方式不对。
- **修复**：构造坏数据前先 `.astype(object)`，并在测试里写清楚原因。
- **回归**：修复后 40 条全过。

### 失败 2：`requirements.txt` 里写了不存在的版本组合

- **现象**：`pip install -r requirements.txt` 报
  `Could not find a version that satisfies the requirement numpy==2.3.4`。
- **原因**：依赖版本是照着指导书写的，没核对本机 Python 3.13 的可选范围。
- **修复**：改成先装、再 `pip freeze` 回填，并把这个差异记录在上面的第四节。
- **教训**：锁文件应该是**装完之后生成**的产物，不是事先猜出来的清单。
