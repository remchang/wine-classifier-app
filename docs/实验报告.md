## 一、需求分析

### 1.1 要解决的问题

机器学习作业最常见的失败模式不是"模型不准"，而是：
**模型只在 Notebook 里活着**。具体表现为三种：

1. **别人用不了**——没有任何能操作的入口，只能看截图。
2. **结果对不上**——训练时做了标准化，推理时忘了做；或者列顺序换了。
   这种错误最恶心：**不报错，但结果全错**。
3. **说不清来历**——过两天自己都不记得这个 `.pkl` 是用哪份数据、
   哪个版本的库、哪些特征训出来的。

### 1.2 需求拆解

| 编号 | 需求 | 验收方式 |
| --- | --- | --- |
| R1 | 定义清楚任务、样本单位、标签、主指标 | 模型卡第一节 |
| R2 | 划分可复现，且没有数据泄漏 | 同种子两次划分一致；预处理器在 Pipeline 内 |
| R3 | 至少两种算法在同一协议下比较 | 相同 5 折分层 CV 的结果表 |
| R4 | 报 Accuracy / Precision / Recall / F1 / 混淆矩阵，说明平均方式 | 界面「模型信息」页 |
| R5 | 保存完整 Pipeline，应用能加载并实时预测 | 关掉界面重启，仍能预测 |
| R6 | 应用校验输入并显示模型版本与不确定性提示 | 输入缺列/非数字有中文提示；有置信度 |
| R7 | 训练脚本、模型文件、元数据可复现 | `model_meta.json` 含 SHA256 与版本 |
| R8 | 至少一项自主功能，且**有量化证据** | 阈值分析表 + 批量容错测试 |

### 1.3 非目标

- 不做超参数搜索。本实验重点是 Pipeline 工程化，加网格搜索会让"两算法同协议比较"失焦。
- 不做概率校准、漂移监控（写进已知限制，不假装做了）。
- 不做图像/文本分类（Wine 是纯数值表格）。

## 二、设计与关键决策

### 2.1 分层结构

```
数据层    shuju.py      加载 / 质量检查 / 分层划分 / Schema 整理
          ↓
特征层    tezheng.py    预处理 + 模型 → Pipeline（唯一定义预处理的地方）
          ↓
训练层    xunlian.py    CV 比较 → 选优 → 一次最终测试 → 保存
          ↓
推图层    yuce.py       加载校验 / 单条 / 批量 / 阈值评估
          ↓
界面层    app.py        只调 yuce.py，不直接碰 sklearn
```

**为什么要分这五层**：`app.py` 一行 sklearn 的代码都不写。
这样以后换模型（比如换成 XGBoost），只需要改 `tezheng.py`，
界面完全不用动。这是"解耦"在一份作业里能做到的最小示范。

### 2.2 决策一：预处理必须进 Pipeline（本实验最重要的一条）

第一版我差点写成这样：

```python
# ❌ 错误写法
scaler = StandardScaler()
X_biaozhunhua = scaler.fit_transform(X)          # 在全量数据上 fit！
X_xl, X_cs, y_xl, y_cs = train_test_split(X_biaozhunhua, y)
```

这样 `scaler` 的均值和方差里已经含了**测试集的信息**，
测试集分数会偏乐观。这就是标准的数据泄漏。

正确写法是把 scaler 放进 Pipeline：

```python
guan = Pipeline([("yuchuli", Pipeline([("buchong", SimpleImputer(median)),
                                     ("biaozhunhua", StandardScaler())])),
                 ("moxing", moxing)])
cross_validate(guan, X_xl, y_xl, cv=fen)
```

`cross_validate` 在每一折里都会重新 `fit` 一遍 Pipeline，
所以 scaler 只见过该折的训练部分。

**三种写法的对比**（这也是报告里最该讲清楚的一点）：

| 写法 | 泄漏？ | 推理时需要手工对齐？ | 结论 |
| --- | --- | --- | --- |
| 先 fit 全量再划分 | **是** | 是 | 错 |
| 在训练集 fit，另行保存 scaler | 否 | **是**（忘记就静默出错） | 能用但危险 |
| 全部放进 Pipeline 一起存 | 否 | 否 | **选这个** |

### 2.3 决策二：分层划分

wine 三类是 59 / 71 / 48。不分层时，小类别在 25% 的测试集里
可能只剩 10 个左右，指标的随机波动会大到没有参考价值。

`stratify=biaoqian` 让训练集和测试集的类别比例基本一致。

**为什么不用 GroupShuffleSplit**：wine 每行是一个独立的酒样本，
不存在"同一个主体有多行"的情况，所以没有分组泄漏风险。
判断依据写在 `src/shuju.py` 的文档字符串里——如果换成"同一用户多条记录"的数据集，
就必须换成 GroupKFold。

### 2.4 决策三：主指标选 macro F1

| 候选 | 问题 |
| --- | --- |
| Accuracy | 被大类带偏；三类不均衡时会掩盖小类的糟糕表现 |
| Precision / Recall | 单独看任何一个都片面 |
| **macro F1** | 三类同等看待，兼顾误报和漏报 |

同时报 `weighted` 版本，因为它更接近整体观感。**只报一个容易误导**，
所以界面上两组都给，并注明平均方式。

### 2.5 决策四：测试集只评一次（结构上保证）

```python
def shiji_xunlian(...):
    ...
    bijiao = [jiaocha_yanzheng(...) for ...]      # 选模型只看 CV
    zui_hao = sorted(bijiao, key=-f1)[0]
    guan.fit(X_xl, y_xl)
    ceshi_jieguo = zui_zhong_pingjia(guan, X_cs, y_cs)   # ★ 全流程只此一处
```

`zui_zhong_pingjia()` 没有出现在任何循环里。
想"用测试集挑模型"就必须改流程结构，改不动就说明约束生效了。

### 2.6 决策五：元数据 + 加载时校验

`model_meta.json` 存的东西：

| 字段 | 为什么要有 |
| --- | --- |
| `huanjing.scikit_learn` | 跨主版本反序列化不保证兼容 |
| `tezheng_ming` | 列顺序错了会**静默**出错，必须能校验 |
| `leibie_ming` / `leibie_yingshe` | 把 0/1/2 翻译成类别名 |
| `shuju_zhiwen_sha256` | 以后表现不对，能确认当时用的是不是这份数据 |
| `moxing_sha256` | 确认模型文件没被换过 |
| `git_commit` | 追溯是哪一版代码训出来的 |
| `kua_jia_yanzheng` / `ceshi_ji` | 完整指标，不用回头重跑 |
| `gailv_jiaozhun_shuoming` | 明确写"未做概率校准"，防止概率被误解 |

加载时校验三件事：**库主版本、特征顺序、标签映射**。
任何一条不过就抛 `MoxingCuowu`，界面给出可操作的提示。

**宁可拒绝加载，也不要静默给出错误预测**——这是本次实现里最认同的一条原则。

## 三、实现要点

### 3.1 Schema 整理：为什么这么小心

界面传进来的是一个 dict，dict 的顺序是**不保证**的。
而 sklearn 的 Pipeline 内部是**位置敏感**的：
特征顺序一变，预测结果就变，而且**不会报错**。

所以 `zu_canshu_zi()` 做三件事：

```python
# ① 检查有没有缺字段
# ② 检查每个值能不能转成 float
# ③ ★ 严格按 lie_ming 的顺序重建 DataFrame
return pd.DataFrame([[float(zhi[c]) for c in lie_ming]], columns=list(lie_ming))
```

③ 是不出错的关键。有一条专门的测试 `test_zu_canshu_zi_an_lie_ming_paixu`
断言"字典顺序打乱，输出列顺序仍然正确"。

### 3.2 批量预测的逐行容错

实验要求："批量预测要返回每行错误，不因一行坏数据使整批无结果。"

```python
for i, (_, hang) in enumerate(biao.iterrows()):
    yuan_hang = i + 1
    try:
        ...校验这一行...
        hao_hang.append((yuan_hang, zidian))
    except ShujuCuowu as e:
        cuowu_liebiao.append({"hang": yuan_hang, "yuanyin": str(e)})
```

坏行只记进 `cuowu_liebiao`，好行继续。最后返回三样东西：
结果表、错误列表、统计。

**关键的一致性设计**：批量预测内部调用的校验函数和单条预测是**同一个**
（`zu_canshu_zi`），所以两条路径的结果必然一致。
有一条测试 `test_piliang_he_dan_tiao_jieguo_yizhi` 专门断言这一点。

### 3.3 自主功能的量化证据

阈值分析的核心逻辑（`pinggu_yuzhi`）：

```python
gailv = guan.predict_proba(X_ceshi)
zuida = np.max(gailv, axis=1)          # 置信度
yuce  = np.argmax(gailv, axis=1)
baoliu = zuida >= yuzhi                # 只保留达到阈值的样本
fugai_lv = baoliu.sum() / len(baoliu)  # 覆盖率
zidong_zhunque_lv = (yuce[baoliu] == y_true[baoliu]).mean()   # 覆盖率内的准确率
```

阈值从 0 提到 0.9，会看到覆盖率下降。**这就是自主功能的量化证据**，
不是"加了个滑块"。

但实测结果和我的预期**不一样**，这里如实记录：

| 阈值 | 覆盖率 | 自动准确率 | 转人工数 | 转人工中本来判对的 |
| --- | --- | --- | --- | --- |
| 0.00 | 100.00% | 100.00% | 0 | 0 |
| 0.60 | 95.56% | 100.00% | 2 | 2 |
| 0.80 | 77.78% | 100.00% | 10 | 10 |
| 0.90 | 64.44% | 100.00% | 16 | 16 |

我原本预期"阈值升高 → 准确率上升"。**实际是准确率一直 100%，只有覆盖率在掉。**

原因：随机森林在这 45 个测试样本上本来就全判对了，
**不存在"判错但很自信"的样本**可以阈值过滤。
最后一列最能说明问题——阈值 0.9 时把 16 个**本来判对**的样本也推给了人工。

这反而是个更有价值的发现：

> 阈值机制只在模型存在"高自信的错误"时才有收益。
> 当模型在当前数据上已经接近零错误，加阈值纯粹是增加人工成本。
> 所以"要不要上阈值"的前提，是先用同类数据确认存在此类错误。

**这一点也说明我没有为了结果好看去调参**——如果我想让它好看，
只要换个随机种子让模型错一两个样本，曲线立刻"符合预期"。

有两条测试防止逻辑写反：
- `test_pinggu_yuzhi_qushi_heli`：覆盖率单调不增
- 阈值 0 时的自动准确率必须等于整体 accuracy（定义自洽检查）

## 五、问题与反思

### 5.1 「静默错误」比报错可怕得多

本次最大的收获是理解了**静默错误**这个概念。

预处理器没对齐、列顺序错了、类别编码变了——这些事情**都不会报错**。
模型照常返回一个数字，界面照常显示，只是结论是错的。
而这类错误往往要到"上线之后发现指标跌了"才会被发现。

本项目的所有防御（Pipeline 封装、Schema 校验、元数据校验、加载时版本检查）
针对的都是同一件事：**把静默错误变成显式报错**。

### 5.2 自主功能不能只是"加个控件"

指导书写得很直白：

> 自主功能有评价证据，不只是换模型名称。

一开始我想做的"阈值滑块"其实就属于"加个控件"。
后来补了阈值分析页——把不同阈值下的覆盖率和准确率算出来，
这个控件才有了可以量化的意义。

**反思**：判断一个功能是不是"自主功能"，标准应该是
"能不能拿出一个前后对比的数据"，而不是"代码量多少"。

### 5.3 还没解决的问题

1. **不做分布外检测**。输入超出训练范围时模型照样给答案，不报错也不提示。
   这是当前版本最明显的短板。正确做法是按特征记录训练集的分位区间，
   越界时给出提示甚至拒绝预测。**这次没做，写在模型卡里了。**
2. **样本量太小**。178 条样本下，两算法 macro F1 差 0.01 完全可能在噪声范围内。
   严格来说应该做配对 t 检验或者重复交叉验证，但这次没做。
3. **概率未校准**。界面展示了概率，但明确标注了"不等于真实发生率"。

### 5.4 关于"两算法比较"的诚实态度

选出来的算法未必真的"更好"。在这个样本量下，
逻辑回归和随机森林的表现很接近，差异可能来自随机种子的选择。

诚实的表述应该是："在固定种子 42 的 5 折分层 CV 下，
macro F1 均值较高的是 X"。**而不是**"X 算法更优"。
这一点写进了报告，也体现在模型卡的口径里。

## 六、收获

1. **Pipeline 不是语法糖**，它是防止数据泄漏和训练/推理不一致的**结构性保障**。
2. **测试集只评一次**这条纪律，靠自觉很难守住，靠代码结构才守得住。
3. **元数据是模型的一部分**。只交一个 `.joblib` 等于交了一个无法追溯的黑盒。
4. **静默错误是机器学习工程里最贵的错误**，所有校验都该为了暴露它而存在。
5. **自主功能要有量化证据**，否则和换了个模型名字没区别。

## 七、思考题

**1. 为什么测试集不应在每次调参后反复查看？**

每看一次，就多一分"挑一个测试集上好看的配置"的诱惑。
反复之后，测试集的信息就通过人的选择**泄漏**进了模型，
它不再是"没见过的新数据"。后果是报出来的指标系统性偏乐观，
真实上线表现明显更差。所以选择要在验证集/交叉验证上做，
测试集只在最后用一次。

**2. Accuracy 很高但正类 Recall 很低时，系统是否可用取决于哪些业务代价？**

取决于**漏报**（把正类判成负类）的代价：
- 疾病筛查、欺诈拦截：漏报代价极高，这种系统等于没用。
- 垃圾评论过滤：漏报只是漏掉几条，误报反而会误删正常评论，
  那低 recall 可以接受。

换句话说，指标本身没有意义，**指标乘以业务代价**才有意义。

**3. 完整 Pipeline 与分别保存预处理器和模型相比有什么优缺点？**

| 维度 | 完整 Pipeline | 分开保存 |
| --- | --- | --- |
| 一致性 | 结构上不可能漏做预处理 | 靠人记住，**忘了就静默出错** |
| 泄漏风险 | 无 | 容易在全量数据上 fit |
| 文件大小 | 大一点（带 scaler 统计量） | 小 |
| 灵活性 | 不能单独替换预处理器 | 可以混搭 |
| 调试 | 想看中间步骤要多写几行 | 可以直接看 |

对本实验这种"一个模型服务一个应用"的场景，完整 Pipeline 明显更合适。

**4. 输入分布变化到什么程度时应该提示、拒绝预测或重新训练？**

没有通用阈值，可分三级：

| 级别 | 触发条件（建议） | 动作 |
| --- | --- | --- |
| 提示 | 某个特征超出训练集的 [1%, 99%] 分位区间 | 界面提示"输入超出常见范围" |
| 拒绝自动判定 | 置信度低于阈值，或明显越界 | 标为"待复核"（本项目已实现置信度部分） |
| 重新训练 | 连续多批输入都系统性偏移 | 先做分布对比，再决定重训 |

**本项目的短板正在这里**：只做了置信度维度的"拒绝"，
还没做特征维度的越界检测。这也是后续改进的第一优先级。
